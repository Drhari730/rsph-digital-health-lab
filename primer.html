Builder's rules

Ten things every digital health builder should know

1. Back up everything, automatically

Follow the 3-2-1 rule: 3 copies, on 2 kinds of storage, 1 off-site. Free hosting tiers often keep no backup, so one wrong "reset" can erase exam results permanently.

2. Never put secrets in code

API keys and passwords go in environment variables or a secrets manager, never in GitHub. A leaked key can run up bills or expose data within hours.

3. Identifiable data needs a reason and a lock

India's DPDP Act 2023 applies to student and patient data. Collect the minimum, get consent, restrict access, and keep sensitive data off public AI services.

4. Own your accounts institutionally

Domains, app-store accounts and hosting should be under the institution, with two admins, so a tool never depends on one person's login.

5. Separate test from live

Try changes on a copy (a "staging" environment) before touching the live exam or portal.

6. Keep code in Git

Git records every change so you can undo mistakes. GitHub stores it online and lets others help.

7. Memory decides which AI model you can run

A model roughly needs (parameters × bytes per parameter) of memory. A 70B model at 4-bit needs about 40 GB before it answers a single question.

8. Validate before you trust

An AI tool is a health intervention. Test it against experts (as Diabot does) and report accuracy before real use.

9. Watch the free-tier limits

Free plans sleep, cap storage and change terms. Fine for demos; use a paid or institutional plan for anything students depend on.

10. A human approves every AI output

Minutes, MCQs, clinical answers: AI drafts, a qualified person checks and signs off.
